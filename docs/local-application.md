# Local Blogger application

## Access decision

Blogger runs as a single-person application on the developer's computer. Opening the loopback Next.js server provides an implicit local workspace without an account. Product profiles, scanned links, topics, calendar dates, articles, article versions, image references, and settings are core local workflows. Optional external services can scan sites, research topics, generate text and images, or publish to a configured receiver; manual editing, blank article creation, calendar planning, reading, export, and deletion work without them.

The local server stores versioned structured data under `BLOGR_HOME` or `~/.blogr` and managed image files in its `media` directory. Credentials stay in process environment variables, separate from project data and exports. A versioned ZIP export contains `workspace.json` and managed image bytes under `media/`. It contains no credentials, caches, absolute device paths, or device identity. Import validates the document and media before replacement, limits the expanded size, and gives imported images new names. Deletion names its scope; deleting an article also removes its saved versions, while deleting a topic retains an associated article and detaches it. Unreferenced managed images are removed after edits and imports. The storage adapter serializes writes, checks a monotonic revision, validates the next document, fsyncs a unique temporary file, and atomically renames it. The previous file remains readable after a failed write. A process lock serializes writers sharing one local home; run one Next server for a workspace.

Supported modes are `local-development`, `local-production`, and `test`, selected by typed runtime configuration. Invalid modes fail startup. Local development and production use the same device-scoped repository and loopback-only HTTP. Test uses an isolated temporary store. There is no hosted-production mode or authenticated provider in this local-only product. Application operations use a repository interface with a file adapter; local identity is implicit to the loopback process. Sync is absent, so conflicts mean two edits based on different local revisions; no remote snapshot can replace local data. Reinstalling dependencies or rebuilding the application does not touch `BLOGR_HOME`. Deleting that directory removes local work; copy an export elsewhere for backup. Temporary network loss leaves manual local workflows available and pauses only the selected external services.

The original Clerk, Convex, R2, and Google Cloud Run worker records are external data. The offline [Convex-to-local migration](convex-to-local-migration.md) requires a verified owner ID and downloaded media, and creates an isolated staging folder for review. It never silently copies cloud records into the active local workspace. Keep the original export until the staged data is verified.

## Current implementation

The Next server binds `127.0.0.1` by default. Local development and deliberately selected local production are supported; a production build or server with no `BLOGR_MODE`, `hosted-production`, and invalid values fail startup. Private API routes check a loopback Host and matching same-origin Origin for writes. They return `Cache-Control: no-store`. JSON request bodies have a streaming size limit. External image downloads reject private network addresses, pin the validated address during connection, limit redirects and bytes, and accept only recognized raster formats. ZIP import validates paths, entry count, per-entry size, total expanded size, raster signatures, and the schema before committing.

`src/local/domain/` defines the canonical schema, valid calendar dates, and v0-to-v1 migration. `src/local/application/` defines the repository contract and query/mutation operations. `src/local/server/` contains the file adapter, write lock, managed media, export/import, and external image safety. `src/local/client/` provides local state and query hooks for the existing interface. `src/app/api/local/` exposes the same-origin loopback API. Generated articles and scans are saved before success responses. Long-running results compare the saved product, topic, or article timestamp before committing so a newer edit is not replaced.

Article versions are created when a generated article is regenerated. Manual text and image edits update the current article. Publishing uses an optional webhook token and destination set in the local server environment. The publisher sends locally stored raster images as base64 data, up to 20 images and 10 MB combined; the receiving app must upload them to its own storage and rewrite local references. A receiver success followed by a local status-save failure is reported as a publishing success with a separate local-status warning.

The Settings page downloads backups, imports backups with an explicit replacement dialog, and deletes the selected project with a scope-specific dialog. Article and topic deletion are available from their existing screens. Export a backup to another folder or drive before changing computers or deleting `BLOGR_HOME`. A malformed workspace file is left untouched and produces a restore error. A failed write leaves the previous file in place. There is no automatic cloud migration or cross-device sync.

A backup import accepts up to 1000 managed images, a 512 MB ZIP, and 600 MB of expanded files, with a 20 MB limit for each image. An offline cloud migration can stage unreferenced historical R2 objects in `archive/unreferenced-media`; that archive is separate from the live workspace and is not part of a normal Settings backup.

## Validation and maintenance

`npm test` covers revision conflicts, simultaneous writes, older schema migration and failed migration, malformed/unavailable storage, invalid modes, managed-image backup roundtrips, failed-import media safety, scoped deletion, stale article edits, and calendar reuse. `npx tsc --noEmit --pretty false`, `npm run lint`, and `npm run build` check the whole repository. Tests set `BLOGR_MODE=test` and a dedicated temporary `BLOGR_HOME`.

The format is currently `schemaVersion: 1` in `workspace.json` and export `version: 1`. Add explicit migrations and tests before changing either version. Keep secret fields out of the schema and use environment variables for provider keys. When adding a mutation, route it through the local application operation and repository revision check; use the managed media scope for files created before a long-running commit.
